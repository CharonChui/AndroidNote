## 模型微调 

经典的Fine-Tuning方法包括将预训练模型与少量特定任务数据一起继续训练。在这个过程中，预训练模型的权重被更新，以更好地适应任务。所需的Fine-Tuning量取决于预训练语料库和任务特定语料库之间的相似性。如果两者相似，可能只需要少量的Fine-Tuning，如果两者不相似，则可能需要更多的Fine-Tuning。

但是，在大多数下游任务微调时，下游任务的目标和预训练的目标差距过大导致提升效果不明显，微调过程中需要依赖大量的监督语料等等。至此，以GPT3、PET等为首的模型提出一种基于预训练语言模型的新的微调范式——Prompt-Tuning。该方法的目的是通过添加模板的方法将任务目标转化为与预训练目标相似的形式（如MLM），避免引入额外的参数的同时，最大化利用模型的预训练知识。

Prompt-Tuning主要解决传统Fine-Tuning方式的两个痛点：

- 参数规模过大、计算与存储成本高：在全量微调中，模型的所有参数都会更新。对于大模型，这意味着显存占用大、训练速度慢，而且每个下游任务都要保存一份完整的模型权重，存储开销巨大。
- 迁移与多任务场景下的效率低：Fine-Tuning 每个任务都要训练一份新模型，不能很好地在多个任务之间共享大模型参数。导致一个任务一份大模型，难以高效适配多任务、多场景。



## Prompt - Tuning(提示微调)

超大规模的Prompt-Tuning方法，分别为：

- 上下文学习 In-Context Learning（ICL）：直接挑选少量的训练样本作为该任务的提示；
    通过上下文示例让模型理解任务，而无需显式训练。常用的In-contenxt learning方法包括:   
    - zero-shot learning: 给出任务的描述，然后提供测试数据对其进行预测，直接让预训练好的模型去进行任务测试
    - one-shot learing: 在预训练和真正翻译的样本之间，插入一个样本作为指导，相当于给一个例子。
    - few-shot learning: 插入多个样本作为指导，相当于给多个例子。


- 指令学习 Instruction-Tuning：构建任务指令集，促使模型根据任务指令做出反馈；
    通常是在一个预训练大模型的基础上，收集大规模指令-响应对，并将这些指令转化为自然语言提示（prompt）输入模型，通过监督微调（Supervised Fine-Tuning, SFT）让模型学会按照指令生成符合预期的输出；训练时将指令与上下文拼接成输入序列，目标是最大化模型对正确响应的生成概率，从而让模型在推理时对未见过的新指令也能进行符合意图的生成。
    
- 思维链 Chain-of-Thought（CoT）：给予或激发模型具有推理和解释的信息，通过线性链式的模式指导模型生成合理的结果。

    CoT 没有像 ICL 那样简单地用输入输出对构建提示，而是结合了中间推理步骤，这些步骤可以作为大模型的输入。简单来说，思维链是一种离散式提示学习，更具体地，相比于之前的上下文学习（即不进行训练，将例子添加到当前样本输入的前面，让模型一次输入这些文本进行输出完成任务），思维链多了中间的推导过程提示。
    




遇到"模型效果不好",专家的排查顺序是一个成本递增的阶梯,绝不上来就微调:

提示词工程(几分钟) → RAG外挂知识(几天) → 微调(几周+算力钱) → 预训练(别想了)

### 微调方法地图

- 全参微调(Full Fine-tuning):更新全部参数。7B 模型全参训练要 100GB+ 显存,个人玩不起,也容易把通用能力练丢(灾难性遗忘)
- LoRA(Low-Rank Adaptation):冻结原模型,只在每层旁边加两个小矩阵——一个大矩阵可以近似拆成两个"瘦长"小矩阵相乘,这就是低秩分解,参数量因此骤减——只训练这不到 1% 的新参数。效果接近全参、显存省一个数量级,是当前微调的绝对主流
- QLoRA:把冻结的原模型量化成 4bit 再做 LoRA,显存再省一半——7B 模型 16GB 显存(一张免费 Colab T4)就能微调
- SFT(Supervised Fine-Tuning,监督微调):用"问题-标准答案"对训练,教模型"照着学"。你要做的 99% 是这个
- RLHF / DPO(偏好对齐):用"回答 A 比回答 B 好"的偏好数据训练,教模型"哪种更好"。大厂对齐团队做的事,了解概念即可

最常见组合 = SFT + QLoRA。



### LoRA

LoRA微调的全称是Low-Rank Adaptation，这种方法通过引入低秩矩阵分解，可以通过仅训练少量参数实现大模型的适配。  




### 模型微调


微调(Fine - tuning)是指在已经预训练好的大规模模型基础上，通过进一步训练来适应特定任务或数据集的过程。   

这一过程体现了迁移学习的思想，即利用预训练模型在通用数据上学习到的知识，通过微调使其更好的服务于特定的应用场景。 


#### 微调的主要步骤: 

1. 选择预训练模型: 从现有的大型预训练模型(如qwen、deepseek、llama等)中挑选适合任务需求的模型作为基础。  

2. 准备数据集: 为特定任务准备高质量的训练和验证数据集，确保数据与目标任务紧密相关。  

3. 调整模型结构: 根据任务需求，可能需要对模型进行微调，如增减层数、调整激活函数等。 

4. 设置训练参数: 包括学习率、批处理大小、训练轮次等，这些参数将直接影响微调效果。   

5. 开始训练: 在选定数据集上迭代训练模型，并观察验证集上的表现，适时调整训练策略。  

6. 评估与部署: 使用测试集评估微调后的模型性能，满足要求后即可部署到实际应用中。   

以上就是AI模型微调步骤，不管是模型微调和模型训练都少不了模型微调和模型训练需要的数据集。我们知道要想微调和训练模型数据集非常重要。数据集都是靠人工标注或者是通过程序来实现，对非技术人员不太友好，换句话说微调数据集制作门槛就非常高，普通小白是很难上手的。




很多新手一遇到模型效果不好就像微调，这往往是错的第一反应。  

效果不好需要按这个顺序排查:   

- 效果不好？ 
- 先优化 Prompt
- 还不行？ 用RAG补充知识
- 还不行？ 考虑更换更强的模型
- 以上都试过扔不满足 才考虑微调  

为什么微调排最后？ 因为它的成本最高(要数据、要算力、要时间)、更新最麻烦(数据变了得重训)、且大部分问题Prompt + RAG就能解决。  

微调真正擅长解决的是:   

- 风格/格式的稳定固化: 让模型永远用某种特定语气、格式输出(Prompt反复叮嘱都不稳定时)
- 特定任务的能力强化: 某个很垂直、Prompt教不会的任务。  
- 让小模型学会大模型的某项能力: 省成本 

注意区分: 微调是教模型新的行为/风格，RAG是给模型新的知识，想让模型知道最新信息，需要用RAG而不是微调。   


### 微调的基本概念

PEFT(大模型参数高效微调)

参数高效微调方法（Parameter-Efficient Fine-Tuning，PEFT），PEFT 方法仅微调少量或额外的模型参数，固定大部分预训练参数，大大降低了计算和存储成本，同时最先进的 PEFT 技术也能实现了与全量微调相当的性能。

目前应用较多的PEFT方法主要分为三大类：

- Prefix/Prompt-Tuning：在模型的输入或隐层添加 k个额外可训练的前缀 tokens（这些前缀是连续的伪 tokens，不对应真实的 tokens），只训练这些前缀参数；
- Adapter-Tuning：将较小的神经网络层或模块插入预训练模型的每一层，这些新插入的神经模块称为 adapter（适配器），下游任务微调时也只训练这些适配器参数；
- LoRA：通过学习小参数的低秩矩阵来近似模型权重矩阵 W的参数更新，训练时只优化低秩矩阵参数；


#### 全量微调 vs LoRA

- 全量微调: 调整模型的全部参数，效果好但要巨大算力(几十上百GB显存)，个人几乎做不了。  

- LoRA(低秩适配): 只训练一小部分附加参数，冻结原模型主体。显存需求大幅降低，一张消费级显卡就能微调小模型，是个人和中小团队的主流选择。  

类比: 全量微调像重新装修整栋房子，LoRA像只换软装(家具、窗帘)---花小钱办大部分事，还能随时换回来。   

#### 微调需要什么

1. 数据: 一批输入 -> 期望输出 的高质量样本，数据质量决定一切，几百上千条精心准备的数据，往往胜过几万条脏数据。  
2. 一个基座模型: 开源的如Qwen、Llama、ChatGLM等。
3. 算力: 一张够用的GPU(本地或租云GPU)
4. 工具: 如LLaMA-Factory(新手友好，图形界面能拉起微调)、Unsloth(块且省显存)、Hugging Face PEFT库。   

#### 微调数据长什么样  

通常是这样的对话样本(JSONL格式，每行一条)

```json
{"messages": [{"role": "user", "content": "把这句话改写得更正式：这bug我搞不定"}, {"role": "assistant", "content": "此缺陷目前尚未定位到根因，需进一步排查。"}]}
```
准备几百上千条这样的样本，就是微调的核心工作。  

如果不想折腾本地环境，很多云厂商(包括模型厂商本身)提供托管微调服务:    
你上传数据 -> 平台帮你训 -> 给你一个微调后的模型接口调用。  

#### 数据准备：微调成败的80%

两种通用格式:  

- Alpaca格式(单轮指令)
```
{
  "instruction": "把用户的旅行需求解析成JSON",
  "input": "我想十一带爸妈去西安玩四天,预算八千",
  "output": "{\"city\": \"西安\", \"days\": 4, \"budget\": 8000, \"companions\": \"父母\", \"date\": \"十一假期\"}"
}
```

- ShareGPT格式(多轮对话，Agent场景更常用)
```
{
  "conversations": [
    {"from": "human", "value": "北京天气怎么样?"},
    {"from": "gpt", "value": "[TOOL_CALL:get_weather:city=Beijing]"},
    {"from": "human", "value": "[工具返回] Beijing: 晴 25°C"},
    {"from": "gpt", "value": "北京今天晴,25度,很适合出门!"}
  ]
}
```
把你 Agent 的工具调用轨迹做成训练数据,微调后小模型也能稳定输出你的工具调用协议——这是 Agent 微调最常见的实战场景。

##### 微调数据从哪来

- 生产日志清洗(最好的来源):从你的 Agent 日志里挑出"回答得好"的对话,人工修正后入库
- 大模型蒸馏:用 DeepSeek/GPT-4 级模型批量生成高质量问答,教给 7B 小模型(注意各家 API 的服务条款)
- 人工编写种子 + 扩写:手写 50 条典型样本,让大模型仿写扩充到 500 条,再人工抽查

##### 数量与质量

- 学格式/语气:300~1000 条就有明显效果
- 学领域任务:3000~50000 条
- 铁律:质量 > 数量。100 条精心校对的样本,胜过 10000 条脏数据;脏数据不仅没用,还会教坏模型

### 4.4 训练完必须做的两个检查

1. **对照评估**:准备 20~50 条**训练集里没有的**测试题,微调前后各跑一遍,肉眼对比 + 让 GPT-4 级模型当裁判打分(第 10 篇的 LLM-as-a-Judge)
2. **通用能力回归**:问几个与训练任务无关的常识题,确认没有灾难性遗忘(比如练完工具调用后连"你好"都回不好了,就是训过头:减少轮数或降低学习率)


#### QLoRA
QLoRA出现的背景和动机:

尽管LoRA已经大大降低了微调的参数量和存储需求，但对于GPT-3 (175B)、LLaMA-65B (65B)、Falcon-40B (40B) 这样参数量巨大的模型，即使是加载模型本身（即使冻结）也需要巨大的GPU内存。例如，加载一个65B参数的16-bit模型就需要大约130GB 的 VRAM，这超出了大多数消费级GPU的能力。

于是Dettmers et al. 于 2023 年在论文 QLoRA: Efficient Finetuning of Quantized LLMs 中提出**QLoRA (Quantized LoRA)** 。

它的核心思想是：通过对预训练语言模型（PLM）进行量化（通常是 4-bit NormalFloat），并结合 LoRA 技术进行微调，从而在极低的内存消耗下，仍然能够高效地微调巨型语言模型，同时保持甚至超越全量 16-bit LoRA 的性能。

QLoRA极大地降低了微调大型模型的硬件门槛，使得在消费级 GPU 上微调数十亿甚至千亿参数的模型成为可能。

QLoRA的特点：

优点：
极低的内存消耗。这是 QLoRA 最显著的优势。可以将训练巨型模型的内存需求降低 3-4 倍，使得在单张消费级 GPU 上（如 24GB VRAM 的 RTX 3090/4090）微调 65B 甚至 70B 参数的模型成为可能。
性能优异：尽管进行了 4-bit 量化，但由于 16-bit 的 LoRA 权重和优化器状态，QLoRA 在许多任务上能够保持与 16-bit LoRA 甚至全量微调相媲美的性能。
训练速度快：由于只训练少量参数且内存效率高，训练速度非常快。
缺点
虽然 NF4 优化了精度，但极端任务或敏感任务可能仍受 4-bit 量化影响。
由于量化和分页机制的存在，训练和问题调试会比标准 LoRA 更复杂。

### 私有化部署：把模型跑在自己机器上

为什么要私有化部署?   

- 数据安全/合规: 敏感数据不能发给第三方API
- 成本: 高频调用时，自己部署开源模型可能比调API便宜
- 可控/离线: 不依赖外部服务，可断网运行。 

代价: 你要自己搞定GPU、运维、性能优化 - 比调API复杂得多。  


### 新手友好的部署工具

- Ollama: 一行命令就能在本地跑开源模型，Ollama提供OpenAI兼容接口，所以只要把base_url换成本地地址就能切换到本地模型
- vLLM: 生产级高性能推理引擎，追求高并发、低延时用，比Ollama复杂，但快很多
- LM Studio: 带图形界面，适合桌面端长线 

### 部署要关心的概念

- 量化(Quantization): 把模型参数从高精度压成低精度(如FP16 -> INT4)，大幅降低显存占用，代价是轻微精度损失。让大模型能塞进小显卡的关键技术。你会看到模型名带Q4、INT8之类标记，就是量化版本。  

- 显存需求: 模型大小 ≈ 参数量 * 每参数字节数。 7B模型FP16大约要14GB显存，INT4量化后约 4~5GB。选模型前先算算你的显卡够不够。  


### vLLM

Ollama适合单人开发，要同时服务几十上百个用户，用vLLM(需要NVIDA GPU + Linux):  

```python3
pip install vllm
vllm serve Qwen/Qwen2.5-7B-Instruct --host 0.0.0.0 --port 8001
# 微调过的模型: vllm serve /path/to/你导出的模型目录
```

vLLM 快在哪:

- PagedAttention:像操作系统管理内存分页一样管理 KV Cache(注意力缓存),显存利用率提升数倍
- Continuous Batching(连续批处理):不等一批请求全部完成,谁的生成结束了就立刻把空位让给新请求——高并发下吞吐量是朴素实现的 10~20 倍

显存估算公式:  

```
推理显存 ≈ 参数量 × 精度字节数 + KV Cache
7B 模型 FP16: 7B × 2字节 = 14GB(权重) + 几GB KV Cache → 24G 卡合适
7B 模型 4bit:  7B × 0.5字节 = 3.5GB + KV Cache → 8G 卡能跑
```
